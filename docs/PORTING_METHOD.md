# 移植方法（本项目执行口径）

本文是六包移植的**做法基准**，不是计划书。后续每一轮工作按本文执行，
偏离本文的改动视为跑偏。口径由用户确定，下面第 1 节是原话口径的落地。

---

## 0. 一句话

**只替换"和系统不兼容的那一层"。原版逻辑、接口、流程一个字不动。**

---

## 1. 硬性口径

1. 保留原包名、原 UI、原资源、原提示、原页面顺序、原交互流程。
2. **接口不动**，实现可以换。原方法签名、Intent、广播、AIDL、回调语义照抄。
   例：原来是 `com.huawei.android.permission.VR`，就还是这个名字，只是实现换成
   通用安卓能跑的东西。
3. 要补的是**华为/麒麟/EMUI/鸿蒙那一层**，把它映射到通用安卓等价能力上；
   不是把产品逻辑重写一遍。
4. 不写替代首页，不伪造连接状态，不跳过准备页/确认页，不用强制跳转充当"打通"。
5. **通用性**：目标是通用安卓 + 华为 VR 设备。任何写死某一台设备
   （厂商号、产品号、固件版本、设备名、节点编号）的写法都不合格。
6. 联网、账号、在线推荐、云配置按已批准范围去掉；不伪造登录或在线授权。
7. 权限不够就走 Shizuku / root 补授权，不靠"宽容模式"糊过去。

---

## 2. 执行步骤（四步）

对每个"跑不起来/画面不对"的现象，按顺序做：

**第一步：跑未改动的原版，找到第一个真实失败点。**
不要从类名猜职责，也不要一上来就改。看真机日志里第一个报错，
或者实测里第一个不反应的按钮。

**第二步：判断这个失败跨的是哪一类系统边界。**
分类只有几种：设备节点 / 系统服务 / 权限 / 显示 / 总线 / 在线依赖。
判断依据是日志里的 errno、avc 拒绝、找不到的路径或服务名。

**第三步：去原厂固件里查这个边界原来是谁提供的。**
EMUI9 工程固件已解包，能查到：
`system/bin/ueventd.rc`、内核镜像（内含各驱动）、`vendor/lib*/hw/*.so`、
`bin/hw/*`、`etc/init/*.rc`、`framework/vr.jar` 等。
**以原厂实现为准，不以推测为准。**

**第四步：用通用安卓的等价机制把这个边界补上。**
优先做到"只改指向、不改代码"。只有确实没有等价机制时，才写兼容实现，
而且它必须**从真实硬件取数据**，不能返回常量。

---

## 3. 动手写兼容实现之前，必须先回答的三个问题

1. **这是不是标准机制？**
   用 AOSP / Linux 头文件对照，不要凭类名猜。
   （本项目实例：看起来是"华为私有 ioctl"的四个命令，对照 `hidraw.h`
   后全部是标准 `HIDIOCGFEATURE/HIDIOCSFEATURE`。）
2. **原厂那个边界提供者是谁？**
   在固件里找到具体文件（驱动名、so 名、rc 文件里的行）。
3. **能不能只改"指向"而不改代码？**
   如果能，就到此为止，不动任何原版代码。

三个问题答不上来，说明还没到写代码的时候。

---

## 4. 证据标准

- 每条结论要有**真机日志**或**原厂文件出处**，二选一或都有。
- 验证"原版行为"时，**必须以 `原包/` 里的原始文件做哈希比对为基准**，
  不能以工作区或 HEAD 为基准。（本项目踩过：用 `git checkout` 还原，
  而 HEAD 里存的就是打过补丁的文件，导致"原版验证"结论无效。）
- 进度分四档记录，不合并：
  **源码已改 / 构建通过 / 单项实测 / 跨模块实测**。
- 生成成功、安装成功、启动成功，都不算功能通过。

---

## 5. 已经踩过的坑（反例，不要重犯）

| 反例 | 错在哪 |
|---|---|
| 去改 `libWalleDev.so`，把厂商号/版本/偏移换成常量、把激活调用改成直接返回成功 | 改错了层。边界不在应用，在"设备节点指错了接口"。改应用既不通用也不忠实，而且假数据让 SDK 走错分支（头盔协议被降到 1.0，真机是 2.0） |
| 用 `setenforce 0` 让读写通过 | 不是方案，只是诊断手段。正确做法是给节点一个有权限访问的标签，保持 Enforcing |
| 用 `git checkout -- <file>` 还原后宣称"用原版验证通过" | 还原基准错了。必须以 `原包/` 原始文件为准做哈希比对 |
| 用 7-Zip 打模块 zip | 丢失 Unix 可执行位，脚本开机跑不起来。必须带 `customize.sh` 或在脚本内 `chmod` |
| 把某个模块单独跑通就当成整链打通 | 主线要六个模块连起来才算 |

## 6. 每轮工作的产出要求（必须落地文件）

每一轮改动都要留下可复查的文件，不留"只在对话里说过"的结论：

| 产出 | 位置 | 内容 |
|---|---|---|
| 补丁/接口审计 | `docs/PATCH_AUDIT.md` | 每个改动的原调用点、替代实现、消费者、验证结果 |
| 离线功能矩阵 | `docs/OFFLINE_FEATURE_MATRIX.md` | 逐屏标注数据来源（本地/在线/混合）与处理方式 |
| 平台接口台账 | `docs/PLATFORM_API_SURFACE.txt` 等 | 平台类签名、实现状态（已实现/接口占位/不可用） |
| 基线哈希 | `docs/BASELINE.md` | 原包与解码树的 sha256 |
| 构建脚本 | `build/*.ps1` | 保证可重复构建 |
| git 提交 | — | 提交信息用「模块 + 动作」，一项改动一次提交 |

## 7. 已按本方法完成的一项（样板，可对照着做下一项）

**问题**：眼镜全程黑屏，SDK 停在"眼镜未就绪"。

**第一步**：跑未改动的原版，日志第一个失败点是
`DevHid: openDevice failed or get vendor data failed!`，且该线程每 10ms 重试一次。

**第二步**：判断边界——是设备节点。它打开 `/dev/hwvr1`，通用内核上不存在该节点。

**第三步**：查原厂固件。内核里有 `drivers/hid/hid_vr.c`，是个 hidraw 分支，
注册 `hwvr%d` 字符设备；`system/bin/ueventd.rc` 给 `/dev/hwvr0`、`/dev/hwvr1`
定的是 `0664 root system`。再对照应用侧的实际调用，发现那四个"私有 ioctl"
就是标准 HID 特性报告读写。

**第四步**：通用安卓上有等价机制，所以**不改任何原版代码**，只把
`/dev/hwvr1` 指向眼镜真实的 HID 控制接口（由协议应答探测选出，不写厂商号），
并给节点一个应用有权打开的标签。

**结果**：原版库零修改，SELinux 保持 Enforcing，厂商号/版本/显示偏移/激活
全部由真实设备应答，IMU 1000Hz 无丢帧，Unity 空间与 3DoF 手柄识别正常。
完整记录见 `docs/PATCH_AUDIT.md` 第 12–13 节。

## 8. 剩余模块按同一方法推进

| 模块 | 先要回答的问题 |
|---|---|
| 显示与空间合成 | 原厂是 AOSP `android.hardware.vr@1.0` HAL + 外接屏 Presentation；华为额外加的是 `hivrar`（HIDL）与麒麟面板库 `libhivr`（低余晖/vsync）。先确认哪些是通用部分、哪些必须各自实现 |
| 手柄（CF20） | 原厂连接与按键语义怎么走的，`vrhandle` 与 Runtime 之间谁通知谁 |
| 视频 / 投屏 | 本地媒体链与 MediaProjection 各自的原调用点 |
| 离线裁剪 | 逐屏分类后再摘，不整体删组件 |
| 主应用 / 桌面 | 原本地入口与空间应用列表的原实现 |

每一项都要走完第 2 节的四步，并在 `docs/PATCH_AUDIT.md` 留下记录。

## 9. 缺失类 / 兼容类的处理流程（强制，后续遇到新类照这个走）

应用编译时引用了某平台类，而通用安卓上没有它 —— 这时**不要凭类名猜、也不要直接手写**。
按下面四步走，顺序不能反。

### 第一步：先查「原厂到底有没有这个类」

```
& .\tools\official-index.ps1         # 原包 + 原厂件 -> build/official-index/*.txt
python tools\compat-source-audit.py  # 交叉比对 -> docs/OFFICIAL_SOURCE_AUDIT.md
```

- `tools/dexdump/DexDump.java` 是只读反汇编入口（`--list` 列类名，或反汇编成 smali）。
  它能读普通 dex、jar、odex+同名 vdex，也能读 EMUI 9 那种 200 字节壳 jar
  配套的 compact dex（官方 baksmali 2.2.7 / jadx 0.9 读不了）。
- 查询来源固定两类，**缺一不可**：
  1. `原包/*.apk` —— 七个原始包（应用自己带的类，含 Runtime 里的
     `assets/hvrframework.dex`）；
  2. `原厂件/*.jar` —— 从华为官方固件里原样取出的框架分片
     （`hwframework.jar`、`hwPartVr.jar`），来源与 sha256 见 `原厂件/README.md`。

### 第二步：分两档处理

| 情况 | 处理 |
| --- | --- |
| 官方有原件，且实现只依赖公开 AOSP API 或自身 | **整族复制官方字节码**，写进 `patches/patch_official_platform_classes.py` 的 `COPY_PREFIXES` |
| 官方有原件，但实现依赖华为系统设施 | **按官方实现移植**：反编译官方类，只把依赖华为的那一步换成通用安卓等价物，其余逐行照搬 |
| 官方确实没有 | 兼容层必须补，按第 3 节的三个问题确认依据后写，并记录在台账 |

两条细则：

1. **复制要放在独立的 dex 目录**。官方类塞进第一个 `smali/` 会撞 64K 方法数
   （实测主应用报 `Unsigned short value out of range: 65874`）。脚本会占用
   `smali_classes<N+1>/`，apktool 按目录名汇编成独立 dex。
2. **复制时剥掉 hiddenapi 标记**（`whitelist` / `blacklist` / `greylist*`）。
   它们只在系统镜像里有意义，apktool 在 api<29 时会拒绝汇编
   （`Hidden API restrictions are only supported on api 29 and above`）。
   剥标记不改任何字节码语义。

### 第三步：记台账

- 类级结论写进 `docs/OFFICIAL_SOURCE_AUDIT.md`（自动生成，别手改）。
- 「按官方移植」的每一类，要在 `tools/compat-source-audit.py` 的 `EXCEPTIONS`
  里写明：官方实现依赖什么、我们把哪一步换成了什么。
- 原调用点、替代实现、消费者、验证结果写进 `docs/PATCH_AUDIT.md`。

### 第四步：验证

至少做到：模块能构建 + 产物 dex 里能看到官方类（或移植后的类）+
真机日志里原来的报错消失。**构建成功、安装成功不等于功能通过。**
