# HUAWEI VR Engine 官方文档：索引与对本次移植的意义

来源页：<https://developer.huawei.com/consumer/cn/doc/graphics-Guides/introduction-0000001097358942>

抓取时间：2026-09-15。同目录 `01-…` 至 `35-…` 是 35 个页面的正文本地快照
（headless Chrome 渲染后提取），页面清单见 `INDEX.md`。仅作离线查阅，版权归华为。

这一套是华为给 VR 内容开发者的官方指南，等于写死了「一个能在 HUAWEI VR Glass 上跑的
应用必须长什么样」。我们的六个包就是按这套规范开发的原厂应用，所以这份文档是判断
「看到的异常是适配问题还是原版设计」的权威参照，比从 smali 反推更直接。

## 一、直接对上当前卡点的条目

### 1.1 图标进引导页、插眼镜进 VR —— 原版就是「一个页面 + 系统侧一跳」

依据：`12-Unity-2D界面提示设置.md`。

原文：「HUAWEI VR SDK 3.5 提供 2D 界面提示功能，该界面包含在
`Assets\Plugins\Android\hvrprompt.aar` 中……开发者只需在自己的 2D Activity 中，
使用以下示例代码跳转到该 Activity，就会弹出提示界面，**插入头盔后就能跳过
VrLauncher，直接启动应用自己的 VR Activity**」

```java
Intent intent = new Intent();
intent.setPackage(getPackageName());
intent.setAction("com.huawei.android.vr.PROMPT");
startActivity(intent);
```

对照我们六个包的 manifest（`decode/<pkg>/AndroidManifest.xml`）：

| 包 | 注册 `com.huawei.android.vr.PROMPT` | 注册 `com.huawei.android.vr.action.MAIN` |
| --- | --- | --- |
| `com.huawei.vrlauncherx` | ✔ `Vr2dStartUpActivity` | ✘ |
| `com.huawei.vrvirtualscreen` | ✔ `Vr2dStartUpActivity` | ✔ |
| `com.huawei.himovie.vr` | ✘ | ✔ |
| `com.huawei.appmarket.vr` | ✘ | ✘ |
| `com.huawei.vrhandle` | ✘ | ✘ |
| `com.huawei.hvrsdkserverapp` | ✘ | ✘ |

结论修正第 17 节的一条表述：`Vr2dStartUpActivity` **不是缺陷，它就是原版的引导页**，
而且它同时挂 `LAUNCHER` 和 `PROMPT` 两个 intent-filter —— 点图标和收到 PROMPT
落到同一个页面，这正是官方语义。

同时确认：**这个页面自己不跳转**。逐行读过
`decode/com.huawei.vrlauncherx/smali/com/huawei/vrlauncherx/activity/Vr2dStartUpActivity.smali`
（826 行）：`onCreate` 只做隐私页判断 + 取 `content://smart_provider/smartabilityset`
的 `knowledgePage` + 填文案；`onResume` 只调 `k()` 弹一个 AlertDialog，`onStop` 关掉它；
全类没有任何 `startActivity` 到 `MainActivity` 的路径。它读的一个属性是
`ro.vr.surport`（华为自己的拼写）。

所以「插入后进 VR」这一跳必然由**系统侧**提供，与第 20/22 节查到的缺件
`com.huawei.vrservice` 是同一条链，不是桌面包该自己做的事。

### 1.2 Android 11+ 的包可见性（`<queries>`）

依据：`09-Unity-AndroidManifest配置.md`。原文要求 Android 11（API 30）及以上在
`manifest` 下加：

```xml
<queries>
  <package android:name="com.huawei.vrhandle" />
  <package android:name="com.huawei.hvrsdkserverapp" />
  <intent>
    <action android:name="com.huawei.vrhandle.service.vrdeviceservice"/>
  </intent>
</queries>
```

实测六个原包：五个带 `<queries>`（`hvrsdkserverapp` 没有，它是被查方，合理），
**但没有任何一个把 `com.huawei.vrhandle.service.vrdeviceservice` 这个 intent 写进去**。

用 aapt2 读原包得到的目标 SDK：

| 包 | minSdk | targetSdk |
| --- | --- | --- |
| `com.huawei.appmarket.vr` | 26 | 29 |
| `com.huawei.vrlauncherx` | 26 | 29 |
| `com.huawei.himovie.vr` | 26 | 29 |
| `com.huawei.vrvirtualscreen` | 26 | 29 |
| `com.huawei.hvrsdkserverapp` | 26 | 26 |
| `com.huawei.vrhandle` | 26 | **31** |

包可见性过滤按**调用方自己的 targetSdk** 生效：targetSdk ≤ 29 的包不受限，
所以前五个不受影响；**只有 `com.huawei.vrhandle`（31）受限**，而它的 `<queries>`
列了 `appmarket.vr / hvrsdkserverapp / vrlauncherx`，是够用的。

另外 `com.huawei.vrhandle` 已经带了 Android 12 的 `BLUETOOTH_SCAN`
（`neverForLocation`）/ `BLUETOOTH_CONNECT` / `BLUETOOTH_ADVERTISE`，
旧的 `BLUETOOTH` / `BLUETOOTH_ADMIN` / `ACCESS_FINE_LOCATION` 都标了
`maxSdkVersion=30`。也就是说蓝牙这条原厂是按 Android 12 新权限写的，
不是我们缺声明。

（旁证：`com.huawei.vrhandle` 还声明了 `android.permission.INJECT_EVENTS` 和
自定义权限 `com.huawei.vrservice.permission.VR` —— 前者是系统签名权限，
后者由缺件 `com.huawei.vrservice` 定义。这两条都指向「依赖系统侧」这一事实。）

### 1.3 手柄按键的原始语义（这就是按键映射的权威定义）

依据：`32-手柄使用指南.md`、`07-Unity-添加HUAWEI-VR手柄.md`。

| 区域 | 动作 | 原语义 |
| --- | --- | --- |
| 触控板上半区 | 点击 | 确定（应用里**不允许**出现「注视点击」） |
| 触控板上半区 | 滑动 | 界面滑动 / 行走，走 SDK API 判断 |
| 正前方扳机 Trigger | 点击 | 确定 |
| 触控板左下方返回键 | 单击 | 由应用弹「是否退出」提示 |
| 触控板左下方返回键 | 长按 ≥3s | 进主界面（VRLauncher） |
| 触控板右下方圆圈键 | 单击 | 直接回主界面 |
| 触控板右下方圆圈键 | 长按 | 方向校准：画面焦点方向当正前方，手柄指向当手柄正前方 |
| 下半区音量键 | — | 系统保留调音量，应用**不能**自定义 |
| 主页键 Home | 单击 <1s | 进 VRLauncher 界面 |
| 主页键 Home | 长按 ≥1s | **视点重置**（不是回桌面） |
| Home + 扳机 | 同时按 <1s | 截图 |

注意最后两条：Home 长按 = 视点重置。第 7 节里「不能把 Home 一律改成视角复位」
这句话要按这里收紧 —— 单击 Home 是回 VRLauncher，长按 Home 才是视点重置，
两者是不同的按键事件，不能合并。

另一条实现细节：原文注明「手柄状态在 `HVRLayoutCore.cs` 的 `Update()` 中更新，
如果要保持应用中所有获取手柄状态的脚本每一帧拿到一致的按键状态，需要手动调整
脚本执行顺序」。这解释了「同一帧里不同模块看到的手柄状态不一致」这类现象，
是原版脚本执行顺序问题，不是链路断了。

### 1.4 左右眼与渲染的硬约束

依据：`06`、`13`、`15`、`16`、`08`。

- `06`：`HVRCamera` 的 `RenderDepthFormat` 默认 24bit；`RenderResolutionScale`
  默认 1，**默认渲染分辨率 1080×1080**；`SinglePass` 只在 Multiview 模式勾，
  普通模式勾了「会出现显示问题」。
- `13`：多相机要用 `HVRExtCamera` 预制件，它下面挂着 **LeftCamera / RightCamera**
  两个相机，分别对应头盔左眼/右眼视图。左右眼的方向、裁剪、深度语义以这一对相机为准。
- `15`：Multiview（SinglePass）与单目渲染 `void EnableMonocularDisplay(bool enable)`
  **互斥**；视频类建议单目，游戏类建议 Multiview。
- `16`：分区渲染四档 `Off / LowQuality / MiddleQuality / HighQuality`；
  开启分区渲染时**不要**用 `HVRExtCamera`。
- `08`：SDK 暂不支持 Vulkan，建议 GLES3；要勾 Multithreaded Rendering。

### 1.5 顶部那条白条的嫌疑对象

依据：`05-Unity-新建工程并导入SDK.md`。导入 SDK 后会自动加两个 UI Layer：
`HVRUILayer`（绘制特定 UI）和 `HVRVolumeUILayer`（画音量弹框），原文明确
「开发者不允许在这两个 UI Layer 上绘制其他内容，也不允许场景中其他 Camera
显示这两个 UI 层」。眼镜里顶部那条与内容不同步的横条，属于这两层的嫌疑最大，
排查时应先确认它是不是系统 UI 层而不是我们的合成错误。

### 1.6 不用眼镜也能在手机上看画面的调试开关

依据：`09`。

```xml
<meta-data android:name="com.huawei.android.vr.sensor.mode" android:value="mobile"/>
```

原文：加在 `application` 下，「如果开发者需要不连接头盔看到手机上的显示」，
**正式发布必须去掉**，仅用于调试。这条对我们做无眼镜调试有直接用处，
但属于「原版就有的调试开关」，不是我们新造的入口。

## 二、这份文档**没有**给的东西（避免再猜）

- **异步投屏 / 前缓冲直出的实现细节没有公开**。文档只到「开发者把渲染交给 SDK」
  这一层，服务端怎么做面板合成没写。
- `26-Unreal-其他接口说明.md` 是当前最完整的接口清单：`GetHMDInfo`、
  `GetHMDOrientationAndPosition`（3DoF 位置恒为 0）、`ResetHMDYaw`、
  `SetHMDPoseLock`、`SetChromaticAberration`（色散开关）、`SetSvsEffect`（SVS 音效，
  需 `MODIFY_AUDIO_SETTINGS`）、`IsLeftHandMode`、`GetHVRControllerTouchpadTouchPos`、
  `StartControllerVibration` 等。这些是 VR Engine 对外承诺的能力边界。
- **没有任何关于 `com.huawei.vrservice` 的内容**。它是系统预装件，不在开发者文档
  范围里，和第 20/22 节的结论一致：那是一个「缺件」，不是文档能补的。
- 目录标题写 `OpenXR平台`，但该分支下三页（`28/29/30`）的内容其实是
  **HUAWEI VR Audio Plugin**（Unity 空间音效插件），`31` 是 FAQ。不要把这一支
  理解成「华为提供了 OpenXR 渲染路径」——`VR Engine 业务介绍` 里提到的
  `OpenXR：1.0.3版本` 指的是平台版本要求，不是渲染后端承诺。

## 三、和移植方法文档的关系

这些条目全部是「原厂就是这么干的」的直接证据，用法和 `PORTING_METHOD.md` 第二节
四步法一致：先拿它确认原语义，再决定兼容层怎么接。

- 判「是不是原版设计」→ 用 1.1、1.3、1.5；
- 判「是不是我们少声明了」→ 用 1.2、1.6；
- 判「渲染参数该取多少」→ 用 1.4；
- 判「会不会白改」→ 用第二节。
